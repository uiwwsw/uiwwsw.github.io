2023년 말, B2B 대시보드의 테이블이 스크롤할 때마다 헤더가 덜컹거리며 사라지는 문제가 있었다. 회의에서 나온 요구사항은 **“헤더는 고정, 열 리사이즈는 유지, 120Hz에서 끊기지 않을 것”**. 그때 만든 실험 버전이 `ux-scroll`의 시작이었다.

## 요구사항 정리와 초기 가설

- 120Hz 모니터에서 **60fps 이상 유지**
- 1만 행짜리 테이블을 렌더링해도 **메모리 피크 500MB 이하** (Chrome Task Manager 기준)
- CSS `position: sticky`로는 헤더-바디 간 리플로우가 빈번해 **스크롤러/콘텐츠를 분리**해야 한다는 가설

초기 구조는 다음처럼 단순했다.

```txt
[ScrollShell]
  ├─ [Scroller] 가상 스크롤 영역 (overflow)
  └─ [Overlay] 고정 헤더/풋터/가이드라인
```

## 구현 과정에서 부딪힌 문제

### 1) 스크롤 이벤트 과다 발생

`onScroll`을 그대로 상태에 반영하니 React 18 배치 업데이트와 충돌했다. 10초 동안 5천 번 이상 렌더링되는 것을 Profiler에서 확인했다. 해결책은 **RAF 기반 디바운스**였다.

```tsx
const rafScroll = (() => {
  let frame = 0;
  return (fn: (y: number) => void) => (evt: UIEvent<HTMLDivElement>) => {
    cancelAnimationFrame(frame);
    const y = (evt.target as HTMLDivElement).scrollTop;
    frame = requestAnimationFrame(() => fn(y));
  };
})();

<div onScroll={rafScroll((y) => setScrollTop(y))} />
```

이후 동일 데이터셋에서 렌더 횟수가 **5천 → 280회**로 줄었다.

### 2) 리플로우 폭탄

헤더/바디를 서로 다른 컨테이너에 둔 탓에 가로 스크롤이 어긋났다. `scrollLeft` 동기화를 `pointermove`와 `scroll`에서 모두 처리하니 CSS가 매번 reflow를 일으켰다. 최종적으로는 **가로 스크롤은 CSS translate, 세로 스크롤만 native**로 결합했다.

```tsx
{% raw %}
const Header = ({ scrollLeft }: { scrollLeft: number }) => (
  <div
    className="sticky top-0 z-20 h-12 border-b border-slate-800"
    style={{ transform: `translateX(${-scrollLeft}px)` }}
  >
    {/* 컬럼 헤더 */}
  </div>
);
{% endraw %}
```

### 3) 메모리와 GC 프리징

가상 스크롤 범위를 2,000행으로 넓혀 버렸더니 Chrome에서 메모리가 **720MB**까지 치솟았다. 리스트 항목을 `React.memo` + `keyed window`로 줄이고, 스켈레톤을 SVG 한 장으로 통일했더니 평균이 **410MB**로 내려갔다. Lighthouse Performance도 68 → 82로 개선.

## 지금 남은 것과 배포 계획

- 가로 스크롤 위치를 `useSyncExternalStore`로 공유하는 실험을 진행 중이다.
- Storybook에서 4가지 테이블 타입(정렬/리사이즈/드래그/체크박스)을 **cypress component test**로 돌려 `scrollTop`/`scrollLeft`가 유지되는지 확인하고 있다.
- npm 패키지로 배포하기 전까지는 **사내 패키지 레지스트리**(verdaccio)에 퍼블리시해 테스트할 예정.

정리하면, `ux-scroll`은 스크롤 이벤트를 최소화하고 레이아웃을 분리한 뒤 120Hz 모니터에서 프로파일링했을 때 프레임 드랍 없이 동작했다. 남은 일은 API를 정돈하고, 타입 선언을 정제해 외부에서도 바로 쓸 수 있게 만드는 것이다.
